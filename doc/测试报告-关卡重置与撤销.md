## 三、实施中发现并修复的既有缺陷

**≤980px 视口下整页横向溢出（v0.5.0 既有问题，非本次引入）**

修复前实测：

| 视口宽 | 文档 scrollWidth | 溢出 |
| --- | --- | --- |
| 1440 / 1200 / 1000 | 1425 / 1185 / 985 | 否 |
| 980 | 3700 | 是（+2720） |
| 900 | 3700 | 是（+2800） |
| 760 | 3700 | 是（+2940） |
| 640 / 500 / 390 / 360 | 3696 | 是（+3056 … +3336） |

`documentElement.scrollWidth` 恒为约 3700px，与视口宽度无关。根因是窄屏断点把桌面用的
`270px minmax(0, 1fr)` 覆盖成了裸 `1fr`：

```css
@media (max-width: 980px) {
  .course-layout { grid-template-columns: 1fr; }   /* 裸 1fr → 自动最小尺寸 = min-content */
  #levelList { display: flex; overflow-x: auto; }
}
```

`1fr` 的自动最小值等于网格项的 `min-content`，而 `.level-sidebar` 未声明 `min-width: 0`，
于是 `#levelList` 内三组横排关卡（每项 `flex: 0 0 190px`）的 `min-content` ≈ 3652px 被顶成整页最小宽度。
**`overflow-x: auto` 无法阻断这条链路**——它只对弹性/网格项目的自动最小尺寸生效，
而 `#levelList` 是 `nav` 的普通块级子元素。

修复：窄屏断点改 `minmax(0, 1fr)`，`.level-sidebar` 补 `min-width: 0`，
并把 `.course-topbar`、`.practice-grid`、`.lesson-grid`、`.fixed-config` 的单列断点统一为 `minmax(0, 1fr)`。
修复后 360–1440px 全宽度扫描**均无横向溢出**。

## 五、验证工具的使用注意（踩坑记录）

首次运行 I08 时脚本报 `viewport: 1560×3376`，看起来像页面布局崩了，实际是**脚本自己测错了**：

`Emulation.setDeviceMetricsOverride` 的 `mobile: true` 会让 Chrome 在内容超出时**扩张布局视口**，
实测设 `width: 390` 后 `window.innerWidth` 返回 **1560**（390 的 4 倍），于是「窄屏测试」实际以桌面宽度测量，
I08 的断言完全失效。**改用 `mobile: false` 后 `innerWidth` 才正确返回 390。**

配套结论：`--window-size=390,844` 启动 Chrome 也拿不到 390 视口——
Windows 上窗口宽度被**钳到最小 500px**（实测 `innerWidth=500`），故窄屏必须走 CDP 覆盖而非窗口尺寸。

因此脚本中加了两道守卫，避免再次静默测错：

```js
await send("Emulation.setDeviceMetricsOverride", { width: 390, height: 844, deviceScaleFactor: 1, mobile: false });
await new Promise((r) => setTimeout(r, 300));
const narrowInner = await evaluate("window.innerWidth");
if (narrowInner !== 390) throw new Error(`窄屏视口未生效：期望 390，实际 ${narrowInner}`);
```

> 另注：v0.5.0 的测试报告曾记录「当前浏览器控制后端不提供临时 viewport 能力，未执行自动化移动视口截图，
> 窄屏规则已通过 CSS 构建检查」——**该结论不成立**。CDP 一直具备该能力，当时是使用方法有误；
> 「通过 CSS 构建检查」也不构成窄屏验收。本次为 390px 窄屏与 I08 补上了真实测量与截图。
