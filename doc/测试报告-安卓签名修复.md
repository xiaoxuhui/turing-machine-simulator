# 安卓签名修复报告（turing-machine-simulator）

> 日期：2026-09-28（修订 2026-09-30：补第五章「v0.5.0 发版与线上核对」）
> 分支：`android-apk`
> 本机环境：Windows，**无 JDK / 无 Android SDK / 无 aapt** —— 全部核对均为静包解析（Python + openssl）
> Node.js 22.22.2

## 一、为什么要修

v0.3.1（2026-09-11 发布）的 APK 由 GitHub Actions **当次临时生成的 debug 证书**签发，
私钥没有保存。后果：**装了 v0.3.1 的用户，将来升级任何新版本都会被系统拒绝**
（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），现象是「明明有新版本，却一直更新不了」。

这与 EML（v1.2.0）、light_game（v1.1.0）、conway（v0.16.0）是**同一个坑**，那三家已重发包解决。
turing 是四个项目里最后一个，且当时**连修都没开始**（`android/app/` 下既无 keystore，也无 `signingConfig`）。

## 二、根因（三个，不是一个）

| # | 根因 | 形态 |
|---|---|---|
| 1 | **签名不固定**：`.gitignore` 未涉及 keystore，但模板要求的 `android/app/debug.keystore` 从未生成、从未入库，`build.gradle.kts` 也没有 `signingConfigs` 块 | 隐患型：首个包看不出问题，发下一个才炸 |
| 2 | **结构测试从未在 CI 执行**：`tests/android-shell.test.js` 基于 `node:test`，被 `vite.config.ts` 的 `test.exclude` 挡在 vitest 之外（注释称"由 `pnpm run test:android` 运行"），但 `ci.yml` 只跑 `pnpm run check`（= vitest + build），**从未调用过 `test:android`** | 门禁摆设：11 条断言实际跑了 0 条 |
| 3 | **CI 不覆盖活跃分支**：`ci.yml` 的 `push.branches` 只写 `[main]`，而本仓库的活跃开发分支是 `android-apk` | 该分支上 15 个提交（含整块关卡功能）**未受任何检查** |

三者的共同后果：**安卓外壳这条链路在 CI 里等于没有防线**。
根因 2 与 3 是排查根因 1 时顺带发现的 —— 若不修，本次新增的 keystore 断言同样不会被执行。

## 三、修复内容

### 3.1 固定 debug 签名（根因 1）

按 `mini-app-harness` 的 `web-app-to-android-apk` 技能规范，用 openssl 生成 PKCS12
（本机无 JDK，`keytool` 不可用；PKCS12 而非 JKS，故 gradle 必须显式 `storeType`）：

```bash
openssl req -x509 -newkey rsa:2048 -nodes -days 10950 \
  -keyout key.pem -out cert.pem \
  -subj "/CN=Turing Machine Simulator Debug/O=xiaoxuhui/C=CN" -sha256
openssl pkcs12 -export -in cert.pem -inkey key.pem \
  -out android/app/debug.keystore -name androiddebugkey -passout pass:android
```

- `android/app/debug.keystore`（2754 字节）**入库**；`.gitattributes` 补 `*.keystore binary`
- `android/.gitignore` 加注释，写明**不要**给 keystore 加忽略规则（该文件无 `*.keystore` 规则，本来就能入库 —— 这点与模板预期的"加白名单例外"不同，属本项目实际情况）
- `android/app/build.gradle.kts` 新增 `signingConfigs { getByName("debug") { … } }`，
  覆盖 AGP 内置的 debug 签名配置（debug buildType 默认引用同名配置，故无需额外声明引用）

> debug key 的密码在 Android 文档里是公开的（`android` / `androiddebugkey`），**没有保密价值**；
> 唯一重要的是它固定不变。

### 3.2 让结构测试真正执行（根因 2）

`ci.yml` 在 `pnpm run check` 之后追加两步：

```yaml
- run: pnpm run sync:android   # assets 不入库，需先由 dist 同步
- run: pnpm run test:android   # node --test tests/android-shell.test.js
```

顺序有依赖：`check` 里的 `build` 产出 `dist/`，`sync:android` 再据它生成 assets，
最后结构测试才有东西可校验（U03 断言 assets 与 dist 字节一致）。

### 3.3 测试加固（`tests/android-shell.test.js`）

| 变更 | 原因 |
|---|---|
| 新增「固定 debug 签名存在且被 gradle 引用」用例（4 条断言） | 让签名不被静默移除 |
| `versionName` 改为与 `package.json` 的 `version` 比对 | 原先硬编码，每次发版要改三处，必然漂移 |
| `versionCode` 改为形态校验（正整数） | 无可推导真源，"只增不减"靠发版清单人工把关 |
| 补 `SKIP_NO_ASSETS` 跳过逻辑 | assets 在干净检出（CI）上不存在，原写法会误报成失败 |
| 补「资源 XML 注释不含连续两个减号」守卫 | aapt 会直接拒绝，而本机没有工具链、只能等 CI 构建五分钟才发现 |
| 补「开发脚本未进 assets」守卫 | 整目录同步的常见副作用 |

用例数 **8 → 11**。

### 3.4 CI 覆盖活跃分支（根因 3）

- `ci.yml`：`push.branches: [main]` → `["**"]`（回归同目录其他项目的约定 —— conway / light_game 的 `test.yml` 都是 `["**"]`）
- `android-apk.yml`：`push.branches` 补上 `"android-apk"`（否则安卓相关改动在合入 main 前不受构建校验）

## 四、验证证据

### 4.1 v0.3.1 的签名是随机的 —— 实测

用 `web-app-to-android-apk` 技能里的 `apk-v2-cert.py` 从 APK Signing Block 提取 v2 证书：

| | v0.3.1 线上包 | 本仓库新 keystore |
|---|---|---|
| `subject` | `CN=Android Debug, O=Android, C=US` | `CN=Turing Machine Simulator Debug, O=xiaoxuhui, C=CN` |
| `notBefore` | **Sep 11 16:44:08 2026** | Sep 28 14:49:39 2026 |
| 有效期 | 2056-09-03 | 2056-09-20 |
| sha256 指纹 | `8C:A4:90:8B:B6:EB:6F:11:…:C8:C8:A5:63` | `E0:1C:75:3D:08:06:C0:AA:…:80:55:67:37` |
| `cmp` 比对 | ❌ 与 keystore 不一致 | — |

两条**独立**判据同时成立：subject 是 AGP 的默认模板（`Android Debug`），
且 `notBefore` 与那次 CI 的运行时刻（2026-09-11 16:42–16:47）只差约 2 分钟 ——
证书是构建时现场生成的，不是仓库里的固定文件。v0.3.1 的 `versionCode = 1`。

### 4.2 新断言不是摆设 —— 反向探针

| 探针 | 结果 |
|---|---|
| 临时移走 `android/app/debug.keystore` | `not ok 4` —— 「android/app/debug.keystore 缺失 —— 它必须入库…」 |
| 临时把 `versionName` 改成 `9.9.9` | `not ok 3` —— 「build.gradle.kts 的 versionName（9.9.9）必须与 package.json 的 version（0.3.1）一致」 |

### 4.3 门禁漏洞与修复 —— 本地模拟干净检出

移除 `assets/`（模拟 CI 检出后的状态）后按 CI 顺序执行：

| 步骤 | 修复前 | 修复后 |
|---|---|---|
| `pnpm test`（vitest） | 16 文件 / 98 用例全过 —— **全是 `.ts`，`android-shell.test.js` 不在其中** | 同左 |
| `pnpm run test:android` | **CI 里从未执行** | 11/11 通过（`build` → `sync` 8 个文件 → `test`） |
| assets 不存在时的行为 | 原写法会误报失败 | U03 与入口页两条正确 `SKIP`，其余 9 条照跑 |

### 4.4 CI 线上验证（本次修复的完整闭环）

推送 `ce464a4` 后 —— **这是 `android-apk` 分支历史上第一次跑 CI**（3.4 的触发分支修复同时生效）：

| 工作流 | 结果 |
|---|---|
| CI | **success** —— 步骤 7 `pnpm run sync:android`、步骤 8 `pnpm run test:android` 均有执行 |
| Android APK | **success**（约 2 分钟），产物 `turing-machine-debug-apk` |

CI 日志里的 TAP 汇总：`# tests 11` / `# pass 11` / `# fail 0` / **`# skipped 0`**
（0 skipped 说明 assets 已同步，U03 真的跑了，而不是被跳过）。

**最关键的一项** —— 下载该次 CI 的 APK 产物，提取 v2 证书与仓库 keystore 比对：

```
subject    = CN=Turing Machine Simulator Debug, O=xiaoxuhui, C=CN
notBefore  = Sep 28 14:49:39 2026     ← 本机生成 keystore 的时刻
sha256     = E0:1C:75:3D:08:06:C0:AA:…:80:55:67:37
cmp ci.der ks.der  →  字节完全一致
```

这证明 `signingConfigs` 在 CI 上**真实生效**，而不是静默退回随机签名 ——
即：**下一个发布版本的包与本仓库的签名基线一致**，可与后续版本互相覆盖安装。

（那份产物是**修复期**的 CI artifact，`versionCode = 1` / `versionName = 0.3.1` ——
当时尚未动版本号，只用来验证签名配置是否在 CI 生效；正式发版见第五章。）

## 附：核对方法可复现

```bash
PY="<python>"
SK="<mini-app-harness>/技能/web-app-to-android-apk/templates/scripts"

# 1. 导出仓库 keystore 的证书
openssl pkcs12 -in android/app/debug.keystore -nokeys -clcerts -passin pass:android \
  | openssl x509 -outform DER -out ks.der

# 2. 从线上 APK 提取 v2 签名证书
"$PY" "$SK/apk-v2-cert.py" 下载的.apk apk.der

# 3. 字节比对
cmp apk.der ks.der && echo "一致" || echo "不一致"

# 4. 读包内 versionCode / versionName（文件名与 tag 都不算数）
"$PY" "$SK/apk-manifest.py" 下载的.apk
```
